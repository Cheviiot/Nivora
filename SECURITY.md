# Политика безопасности

## Что относится к Nivora

Сообщайте о проблемах в:

- `Staplerfile`, wrappers и lifecycle-скриптах;
- неверных source URL или checksum;
- опасном поведении при установке, обновлении или удалении;
- потере или неожиданной передаче пользовательских данных из-за логики пакета;
- секретах, случайно попавших в репозиторий.

Уязвимости самого приложения следует передавать upstream-разработчику.

## Модель публикации

Nivora принимает осознанную модель TOFU: при первом подключении пользователь
доверяет HTTPS-репозиторию GitHub, аккаунту владельца и выбранной ветке. После
этого SHA-256 фиксирует точный payload каждой версии. Коммиты и теги проекта не
обязаны иметь криптографическую подпись, а проверенные автоматические обновления
могут отправляться прямо в `main` без pull request. Поэтому checksum не заменяет
проверку первого источника и истории изменений.

Nivora не публикует и не хранит в собственных Releases постоянные копии
проприетарных payload. Рецепт обязан загружать их из официального источника
владельца; кратковременная загрузка в изолированном CI допустима только для
проверки и не должна публиковаться как artifact. Собственные Releases разрешены
для исходных или свободно распространяемых сборок Nivora, если лицензия это
позволяет.

## Как сообщить

Для обычной ошибки создайте [issue](https://github.com/Cheviiot/Nivora/issues) и укажите:

- пакет и архитектуру;
- дистрибутив и версию Stapler;
- точную команду и полный текст ошибки;
- ожидаемое и фактическое поведение.

Для ещё не опубликованной уязвимости используйте Private vulnerability
reporting GitHub, если он доступен в разделе Security репозитория. Если его нет,
сначала свяжитесь с сопровождающим через профиль GitHub и не раскрывайте детали
в публичном issue.

Не публикуйте пароли, API-ключи, setup keys, cookies и диагностические архивы без
предварительной проверки.

Подробная модель доверия: [.github/docs/security-model.md](.github/docs/security-model.md).
